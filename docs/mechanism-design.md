# 研发协作与评估机制设计

> 状态:设计定稿(v1),待落地
> 最后更新:2026-07-26

---

## 一、背景

AI 深度介入研发后,原有的团队组织方式出现三个结构性失配:

1. **技能边界被打破。** 前端工程师的工作已被后端工程师直接覆盖,按"负责系统 + 业务线 + 人员技能"划分的固定 Team 结构开始制造瓶颈和闲置。
2. **产能瓶颈从"实现"移到"定义"。** Team Leader 只要能清晰拆解和描述技术方案,实现环节已可移交 AI。
3. **人员产出分化加剧。** 资深研发效率大幅提升,初级研发无事可做。

现状:少于 5 条业务线,原按系统/业务线/技能划分研发 Team。

---

## 二、设计目标与边界

| 要解决 | 明确不解决 |
|---|---|
| 打破 Team 墙,让任务找人而非人找任务 | 初级研发的成长路径(采用自然筛选,详见 §9) |
| 把"定义问题"的能力显式定价、公开可比 | 跨业务线上下文成本(只延缓,靠文档化逐步摊薄) |
| 保住基线工程质量不被悬赏机制吸干 | 分值的绝对精度(前两个季度必然不准) |
| 获得跨业务线的投入/产出可见性 | 组织内的非正式权力结构(只能约束,消不掉) |

**核心理念:Board 是作品记录,不是排位赛。**

记录单位是**作品**,不是人。个人页面是"我有署名的作品集合"。系统不生产排名。

## 三、核心模型:作品与署名

### 3.1 作品条目

Board 的基本条目是一件**作品**(一次交付),不是一个人的账户。

```
作品:竞价链路降延迟 —— P99 80ms → 45ms
业务线 TAG:DSP 70% / ADX 30%
承诺价值档:A
难度档:L
人天:12
Credits:
  定义方案    Alice
  主交付      Bob
  共同交付    Carol
  深度评审    Dave
  上下文支援  Erin
  基线支撑    Frank(Bidding Engine Owner)
完成度档:达成
结论 / 复盘:...
```

### 3.2 为什么记录单位是作品

以人为记录单位的结构,无论怎么调权重,最终都会长成排位赛——因为账户天然可比。以作品为单位则:

- **协作不再是旁账。** 协作者就在作品里,像电影片尾字幕、论文共同作者。一件作品有几个人的名字是**事实陈述**,不是评价,不需要论证"为什么值得给分"。
- **Owner 的基线工作变得可见。** 每件跑在某系统上的作品都带一行 `基线支撑:X`。基线工作最大的困境是"做好了什么都看不见",署名零成本地解决了它——一个季度出现在 40 件作品的 credits 里,本身就是价值呈现。
- **失败可以体面存在。** 一个诚实记录了失败原因和结论的探索型作品,在作品集里是有价值的条目;在分数表里只是一个低分。这才是让人敢碰难题的真正机制——不是罚得轻,而是**做过的事留下痕迹**。
- **协作从零和变正和。** 粗档位计分下,在作品上多写一个名字不消耗任何人的东西。

参照物:学术论文的 CRediT 贡献者分类、电影片尾字幕、开源的 `Co-authored-by` / All Contributors 规范。

### 3.3 署名规则

**提名 + 确认 + 公开。** 交付者在收单时填写 credits,被提名者确认,全员可见。

三条约束:

1. **无人提名的支援等于没发生。** 反过来给交付者诚实的压力——大家看得见谁真的帮了他。
2. **评审 credit 必须挂实质内容**(可见的评审意见),空评审不署名。否则立刻退化为互相点赞刷 credit。
3. **署名 = 权利 + 责任的统一。** 谁署"主交付",谁承担交付后的故障归属。这一条让署名不会通胀成客套。

### 3.4 Credit 角色

| 角色 | 说明 |
|---|---|
| 定义方案 | 把业务目标转化为技术方案、里程碑、验收标准 |
| 主交付 | 主要实现者,承担交付后故障归属 |
| 共同交付 | 认领时约定分工的共同实现者 |
| 深度评审 | 必须留下可见的评审意见,空评审不计 |
| 上下文支援 | 提供业务/系统上下文、排障协助、关键思路 |
| 基线支撑 | 该作品所依赖系统的 Owner |

## 四、任务与计分

### 4.1 两类单

| 类型 | 周期 | 产出 |
|---|---|---|
| **方案单** | 1~3 天 | 业务目标 → 技术方案 + 里程碑 + 验收标准,评审通过即结算 |
| **交付单** | 1~4 周 | 按已通过的方案实现并交付 |

**方案单与交付单可由不同人认领。**

这是整个机制里最重要的结构。产能瓶颈已从"实现"移到"定义",方案单把定义能力显式定价、公开可比、可以被练习。它同时是最好的能力探针:一个季度下来,谁能稳定产出通过评审的方案单,骨干层就清楚了。

> 基线改进类工作(结构性优化、债务清理、可靠性提升)作为交付单开出,需 Owner 确认价值。

### 4.2 三种可见性

- **公开池** —— 任何人可认领
- **限定池** —— 限定条件必须写**上下文**,不写职级
  - ✅ "需要 Bidding Engine 上下文" —— 可通过投入消除的门槛
  - ❌ "需要资深后端" —— 身份标签,会把刚拆掉的墙重新砌起来
- **定向池** —— 指定人,用于 Owner 基线相关和保密项

### 4.3 计分公式

```
分值 = 价值档 × 难度档 × 完成度档
```

| 因子 | 档位 | 谁定 |
|---|---|---|
| 价值档 | S / A / B / C | 出题方(业务线 / 产品 / 技术 Leader),开单时给出并公示 |
| 难度档 | XS / S / M / L / XL | 技术 Leader 们评定,出题人无权定 |
| 完成度档 | 超出预期 / 达成 / 部分达成 / 未达成 | 出题人打,定价小组抽查 |

**刻意使用粗档位,不用连续分值。** 多个主观估计相乘会放大误差;更糟的是精确数字诱导人争论小数点,产生纯政治成本。粗档位争议少、决策快,且诚实地表达了"我们本来就估不准"。

**价值档不锚金额。** 投产前的毛利估算本来就是编的,且广告业务中把毛利归因到具体技术单的混杂因素太多,强行标金额只是把主观判断包装成客观数字。虚标由几位有实际利害的人当面争论解决(见 §4.4)。

### 4.4 定档锚点清单

打架能收敛的前提是有先例。**维护一个已定档作品的锚点清单(每档 3~5 个例子)**,定档时说"这个参照去年 Q3 的 XX 单,那个是 A"。

不设这个清单,同一个争论每季度重打一次,且**吵赢的是嗓门大的人不是对的人**——几位 Leader 都锚在自己线的毛利上,最强势的那条线会持续拿到更多人力。拿具体先例讲话比拿抽象档位讲话容易收敛得多(story point 与判例法的共同做法)。

成本:一个列表,无需流程。

### 4.5 承诺类型

| 类型 | 系数 | 说明 |
|---|---|---|
| 承诺型 | 正常计分 | 时间敏感的业务需求,超时有代价 |
| 探索型 | 折扣计分 | 不确定性高,**允许失败**,失败给部分分并归档结论 |

必须允许失败且不重罚,否则没人碰难题——而难题恰恰是最需要人碰的。

## 五、双账户:悬赏账 + 基线账

每人季度产出 = **基线账** + **悬赏账**。

### 5.1 Owner 契约

每人绑定 0~2 个系统/领域的 Owner 职责,各对应一份契约:

```
系统:Bidding Engine
Owner:Bob
SLO:P99 < 50ms / 超时率 < 0.5% / 月故障时长 < 15min / 竞价成功率 ≥ X%
Error Budget:0.1%
责任边界:不含 上游流量异常 / 第三方 SSP 故障
计价:季度基线分默认满额,按 SLO 达成扣减
```

**关键:默认满分、失守扣减,不是做了才给。**

可靠性工作做好了什么都不会发生。按产出量计价会诱导 Owner 制造可见工作(大重构、大迁移),而不是让系统保持安静。

结构性改进(如 P99 从 80ms 压到 50ms 的架构改动)**不算基线,单独开交付单计价**。

参照:Google SRE 的 SLO / Error Budget 体系,可直接借用其形式。

### 5.2 无 Owner 职责者

悬赏账占 100%,但目标线相应更高。这给团队一个真实选择:**要基本盘,还是全靠打猎。**

> 基线账占比按每个 Owner 的实际负载定,不是普适常数。

## 六、视图

| 视图 | 内容 |
|---|---|
| **作品流** | 首页。按完成时间排序的作品列表,带完整 Credits。形态接近 changelog 或展览,**不是榜单** |
| **个人作品集** | 我有署名的作品列表 |
| **业务线聚合** | 按 TAG 汇总的 投入(人天) · 产出(分值) · 比值 |

### 6.1 关于业务线 TAG

业务线是作品的**维度标签**(可拆分,如 DSP 70% / ADX 30%),**不是独立记分账户**。

分账是错的实现:一个 60% DSP / 40% ADX 的人会有两个半空账户,两条线都不认为他是自己人,跨线工作两边吃亏——刚拆掉的墙会以计分的形式重新长出来。记录要细,聚合要自由,不要为报表需求改记账结构。

**必须有"平台/共享"标签。** 基础设施、公共组件、跨线工具不属于任何业务线;没有这个标签,做平台的人会在所有业务线视图里同时消失,然后没人做平台。

### 6.2 ROI 视图的精度限制(重要)

分值 ≠ 投入。分值 = 价值 × 难度 × 完成度,一个高价值低工作量的单会让那条线看起来"投入很多",其实没有。所以必须投入(人天)与产出(分值)分开呈现。

**放弃金额锚定后,跨业务线的比值只是趋势指标,不是精确对比。** DSP 的 A 和 ADX 的 A 只是"大致对齐",不是同一个单位。

- 同线纵向比(本季 vs 上季):可靠
- 跨线横向比:只能看数量级差异和变化方向

**不要拿这个数字做业务线投入决策。** 看到 1.3 倍差距时,很可能只是两条线的标尺松紧不同。

### 6.3 排名

**公开:** 作品流水与分值(事实)
**不公开:** 总排名(相对位置)——系统不生产名次

人可以自己聚合算出来,但系统不主动推。这个差别在心理上是"作品集" vs "排位赛"。

- **绝不做强制分布。** 微软 stack ranking 的毒性主要来自强制分布,而非打分本身。
- **实时可查流水,分值月度结算。** 实时看分数跳动 vs 月度结算一次,行为模式完全不同,前者必然诱发刷分。

## 七、两个显式机制(不可交给团队约定)

**判据:协调问题可以交给约定,利益冲突问题不能。**

约定能解决"大家不知道尺度在哪"——这类事没人有动机作弊,说清楚就行。约定解决不了"照做对我不利"——这类事上约定只会变成人人都同意、没人会做的场面话。

按此判据,只有两条必须保留为显式机制:

### 7.1 事后价值校准

季度末回看:实际价值兑现 vs 承诺价值档,调整最终分值。

**为什么不能靠约定:** 出题人自己定价值档,虚标零成本。没有校准这个动作,分值通胀是必然而非可能。

### 7.2 改约通道

任何承诺型单,可**公开申请一次改约**,需说明原因。

| 情况 | 处理 |
|---|---|
| 自身原因,主动公开改约 | 分值折减 |
| 外部阻塞,主动公开改约 | **不扣分**,但必须指名阻塞源 → 进月度组织瓶颈报告 |
| 未申请直接超时 | 分值大幅折减 |

**为什么不能靠约定:** 约定"及时同步风险"是无效的——人人都会同意,没人会在自己搞砸时第一个说。它必须是一个**显式的、不丢脸的出口**,有名字、有流程,人才会走。

承诺制的失败案例几乎都失败在同一处:**不是人不努力,是坏消息传不上来。**

第二行还有隐藏收益:承诺制会自动把组织里真正的瓶颈点暴露出来。

## 八、交给团队约定的部分

以下**知道可以做机制化,但刻意不做**,由团队约定处理。出现实际问题后再考虑机制化:

- 作品的最小粒度门槛
- Credit 署名的松紧尺度(建议上线前两周做一次统一校准,过一遍大家提交的条目对齐尺子)
- 交付后故障归属的具体判定(原则:交付者对自己引入的问题负责一段时间,不计入 Owner 基线)
- Owner 评审否决的边界(原则:否决必须给出可执行的整改条件,不能无理由封锁)
- 深度评审的深度标准
- 在飞单数上限
- 组队单的分工与主次

**已明确砍掉的机制:** 信誉分、出题人计分、协作分的增量/切分精细规则、三层单体系、跨线尺子对齐会。

> 砍掉出题人计分的理由:技术 Leader 绩效已与业务线毛利直接挂钩,skin in the game 已经存在,无需另造一套。
> 砍掉协作分精细规则的理由:粗档位下署名不消耗任何人的东西,零和问题自然消失。

## 九、人员策略

**采用自然筛选,不设专门的初级培养机制。** 这是已确认的资源配置判断。

两个必须提前定的操作项:

1. **淘汰规则提前公示。** 最坏的结果是"不救也不淘汰",让人在公开 Board 上挂半年——既废人也污染氛围。规则要先行、要快、要明确。
2. **配套 HR 流程。** 国内"不能胜任工作"需要培训或调岗程序,Board 只能作为证据链之一,不能作为直接依据。

**长期监测指标:方案单通过率的人数分布。** 如果两年后仍然只有固定的 2~3 个人能产出合格方案,说明"定义能力"没有扩散,人才结构问题会以另一种形式回来。

### 作品框架与淘汰目标的张力(必须知晓)

作品框架刻意不生产名次、刻意让失败体面、刻意正和,这些设计**会让淘汰变难**。

**Board 提供事实,不产出淘汰名单。结论由人来下。**

好在事实本身足够清楚——一个人半年内没在任何有分量的作品上署过主要角色,这件事不需要精确分数就能看见。

但如果期待 Board 自动算出末位名单,那作品框架就是错的选择,应该老实做排行榜。**两者不能兼得。** 当前选择是:保留作品框架,淘汰用判断。

## 十、组织与角色

### 定价小组

组成:**负责人 + 2 位产品经理 + 技术 Leader(多位)+ 研发轮值席(季度轮换)**

| 环节 | 谁主导 |
|---|---|
| 价值档 | 出题方给出。多位技术 Leader 绩效锚在各自业务线毛利上,互为制衡 |
| 难度档 | 技术 Leader 们评定,**出题人无权定** |
| 完成度档 | 出题人打,小组抽查 |
| 平台/共享工作定价 | 全组。这是唯一锚不到业务线的部分,最需要人的判断 |
| 跨线争议仲裁 | 全组,负责人仲裁 |

**负责人在定价环节最后发言。** 老板先表态,后面的讨论就结束了,小组会退化成一个人的判断加三个附议。负责人的位置是仲裁和规则维护,不是定价本身。

### Board Steward

负责流程运转、规则维护、申诉受理。**必须有明确的人**——没有 Steward 的机制一定会烂掉:规则会被逐次绕过,但没人负责发现。

## 十一、运行节奏

| 周期 | 内容 |
|---|---|

| 季 | 绩效结论;Owner 契约重签;**对机制本身复盘调参** |

## 十二、上线路径

| 阶段 | 时间 | 内容 | 挂绩效 |
|---|---|---|---|
| 1 | 2 周 | 写 Owner 契约 + 定 SLO | 否 |
| 2 | 2 周 | 建 Board,**只上方案单** | 否 |
| 3 | 1 个月 | 放开交付单,**按任务比例切,不按业务线切** | 否 |
| 4 | 次季度 | 全量 + 正式挂钩绩效 | 是 |

**前三阶段不挂绩效,且必须公开说明。** 分值体系第一个季度必然不准,带着不准的分数做绩效结论会一次性毁掉制度公信力,之后再也修不回来。

**阶段 1 有独立价值。** 即使 Board 全盘不上,把每个核心系统的 SLO 和责任边界写清楚本身就是净收益。这是整个方案里风险最低、回报最确定的一步,建议无论如何先做。

**阶段 2 只上方案单**是最好的低成本试探:成本极低(1~3 天的单),但直接检验"谁能把业务目标翻译成技术方案"。

**阶段 3 按任务类型切而非按业务线切。** 全团队参与,但只有一部分任务走 Board(如所有方案单 + 20~30% 交付单),其余走原流程。这样样本覆盖全员(能真正看到跨线流动),风险由**任务量**控制而非由**人群**控制,退出成本也更低。

### 上线时必须公开声明用途边界

**团队对 Board 是什么的理解,比 Board 实际是什么更能决定他们的行为。**

不明说的话,默认所有人都会假设它是考核工具、是生死簿——然后不管怎么设计,行为都会变成 rat race:挑保险单、不署别人名、不碰难题。精心设计的作品框架会被单方面的想象抵消掉。

上线时明确说出:**Board 是作品记录,不产出排名,不自动决定任何人的去留;绩效结论由人来下,Board 是事实来源之一。** 同时说明前三阶段不挂绩效。

一次性、低成本,但决定头三个月的行为基调。

## 十三、试点指标

事前定死,否则季度末无法判断成败:

| 指标 | 看什么 |
|---|---|
| 完成分值总量 | 交付吞吐是否提升 |
| **跨线流动次数** | 多少任务被非本线人员认领完成——直接检验"打破 Team 墙" |
| 方案单通过率及人数分布 | 定义能力是否集中在少数人手里 |
| **基线 SLO 达成率** | 确认基线没被悬赏机制吸干(最重要的反向指标) |
| 流单率 | 出题质量与难度定价是否合理 |
| 主动离职率 | 预警 |

**Kill criteria(触发即暂停):** 基线 SLO 达成率显著下降,或主动离职率异常。

## 十四、已知风险

### 风险 1:评审瓶颈(最可能的死因)

开源 bounty 的失效公式:**提交成本趋近于零,评估成本不变,系统崩溃。**

AI 让交付成本骤降,而评审和验收成本没降。Board 会加速这个失衡——它奖励产出,只用一个"深度评审 credit"去对冲把关,权重可能不够。

**已采取的对策(供给侧):**
- 完成度打分,让低质量提交不再免费
- 开单时**验收标准必须可判定**——写清楚到交付时双方不会对"是否达成"产生争议的程度。人工判定即可,但标准必须事先明确(注:刻意不做机器自动评审)

**待用的对策(容量侧):** 真到评审排队时,最便宜的杠杆是限制在飞单数(团队约定即可),无需再上机制。

> 注意:完成度打分解决的是**提交质量**,不解决**评审容量**。这是两件事。

### 风险 2:复杂度

原始设计包含十余项机制,行政开销可能超过收益。当前版本已做减法(见 §8),但仍需在运行中持续砍。**新增机制的默认答案是"不加",除非漏洞已经实际发生。**

### 风险 3:协作仍是弱环

Credit 署名让协作可见,但只要主账仍是个人分,协作就永远是二等公民。如果运行中发现协同型任务系统性流单,需要引入"小队认领"作为一等公民,而不是靠加权重修补。

### 风险 4:Steward 单点

如果 Steward 就是负责人本人,所有裁决都是老板裁决,Board 的"事实性"从第一天就打折。已通过定价小组分权缓解(见 §10)。

### 风险 5:AI 时代的倒金字塔

已确认接受此赌注(见 §9)。业内主流判断是"别冻结初级,而是重新定义(Code Generator → System Verifier)",理由是倒金字塔 3~5 年后塌陷。当前选择是相反的赌注,需要通过 §9 的长期监测指标持续观察。
